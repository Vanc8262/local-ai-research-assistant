# RAM during the Stage 2 eval (2026-11-08)

The first eval with RAM logging: 26 reports (5 questions, 2 runs each, local, hybrid and codex modes) over 4.6 hours on the
RTX 3060 PC with 16 GB of RAM. The tool sampled free RAM, swap and the top processes every 15 seconds, 1,149 samples in all. The raw samples are in
`runs/eval-20261108-103541-396170/ram.csv` on the PC; `runs/` is not committed. LM Studio's settings were unchanged:
Gemma 4 E4B QAT at 32K context, reloaded before each question run and every 40 verification calls.

## Summary

| Measure | Value |
|---|---|
| Lowest free RAM | 86 MB (aws-pillars, hybrid, run 2, during verification) |
| Median free RAM | 2.9 GB |
| Time with less than 500 MB free | 14% |
| Time with less than 1 GB free | 22% |
| llama-server RAM, median / peak | 8.5 GB / 11.8 GB |
| Swap used, peak | 1.3 GB |
| Crashes or out-of-memory errors | none |

## What uses the memory

- **llama-server is almost all of it.** It reaches 11.8 GB at peak. The next largest processes are Docker's vmmem at
  2.0 GB (peak, usually about 0.3 GB), Claude at 0.6 GB, Python at 0.5 GB, Defender at 0.4 GB and the LM Studio app
  at 0.4 GB.
- **It grows during long verification.** A fresh load holds about 6.1 GB. During a hybrid verification
  (8 to 29 minutes, about 100 model calls) it climbs to 10.3 to 11.5 GB in every run. The reload every 40 calls only
  brings it back down for a while. Local verifications are short (1 to 4 minutes) and peak at 7.4 to 9.6 GB.
- **Codex runs start high.** The model is reloaded before each question run, not between modes. So the codex run
  inherits the hybrid run's server at 9 to 10.7 GB, and the nomic embedding model is loaded on top. Codex research
  and repair had a median of only 0.8 to 1.7 GB free.
- **Research itself is light.** Local research ran with a median of 5.6 GB free, and llama-server stayed near 5.8 GB.

## Reading against the Nov 5 RAM report

The growth during long verification matches the prompt cache the Nov 5 report blamed: it has no limit and fills
over about 20 minutes. The 6.1 GB a fresh load holds also fits that report's estimate of the locked model copy plus
the vision add-on. These are inferences from the pattern, not measurements of the cache itself.

## Suggested next tests

1. Cap LM Studio's prompt cache and use 1 parallel slot instead of 4, then run the same eval and compare this table.
2. Reload the model between modes as well as between questions, so the codex runs start fresh. This is a one-line
   change in `assistant/evaluate.py`.
3. Lower `RELOAD_EVERY` from 40 to 20 for hybrid verification, if the cache cap alone doesn't keep it under about 9 GB.
